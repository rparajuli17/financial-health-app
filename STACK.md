# Stack Decision — Financial Health App

**Decided:** Nov 18, 2026 (Step 3, GitHub issue #3)
**Decision:** TypeScript end-to-end, with Expo used via development builds and custom native code — *not* Expo Go.

## The stack

| Layer | Choice | Role |
|---|---|---|
| Mobile app | React Native + **Expo** (TypeScript), development builds | One codebase for iOS + Android |
| API | Node.js + **Fastify** (TypeScript) | Lean, schema-first HTTP API |
| Server database | **PostgreSQL** via **Prisma** | System of record; Prisma schema doubles as the data-model document |
| On-device database | **SQLite** (expo-sqlite) | Offline-first local entry/cache, syncs to Postgres |
| Business logic | **`packages/engines`** — a shared, pure TypeScript package | Allocation engine + recommendations engine, imported by both app and API; unit-tested with Vitest |
| Passkeys | **SimpleWebAuthn** (server + client) | The reference WebAuthn implementation for the passkey flows |
| Repo shape | **Monorepo** (pnpm workspaces): `apps/mobile`, `apps/api`, `packages/engines` | Shared types and engines across client and server |

## The Expo constraint — and how we handle it

The Entrust Mobile SDK is a native SDK, and Entrust's integration guide states it cannot be used with React Native Expo as-is; the SDK must be imported manually following Expo's own guidance for custom native code. Expo Go (the managed, no-native-code sandbox) is therefore **out**. Instead, this project uses Expo the way Expo supports native SDKs:

1. **Development builds from day one** — the app always runs as a custom development build, never Expo Go. Libraries with custom native code are installed, then a new development build is created (Expo docs, "Add custom native code").
2. **Continuous Native Generation (CNG)** — `ios/` and `android/` are generated by `npx expo prebuild` and not hand-edited or committed as source of truth.
3. **Config plugins for native configuration** — any native project changes the Entrust SDK requires (AndroidManifest, Info.plist, entitlements) are expressed as config plugins, so they survive prebuild regeneration.
4. **A local Expo module wraps the Entrust SDK** — the SDK is imported manually per Entrust's guide and exposed to TypeScript through a local module built on the Expo Modules API. The rest of the app sees a clean TS interface; the native dependency is quarantined in one place.

This is a deliberate portfolio point, not just a workaround: integrating a vendor native SDK into a React Native app via a local module + config plugins is exactly the kind of work mobile/identity roles ask about.

**Sources:** Entrust Identity SDK integration guide (SDK cannot be used with Expo; import manually per Expo's guide) — documentation.identity.entrust.com; Expo docs, "Add custom native code" (development builds, CNG/prebuild, config plugins, local modules) — docs.expo.dev/workflow/customizing.

## Why TypeScript end-to-end

1. **One language across client, API, and engines** — a solo builder learning full-stack compounds every hour instead of splitting attention across languages.
2. **The engines are shared, not duplicated** — the allocation and recommendations logic is the product's brain; as a pure TS package it runs identically in the app (instant feedback) and the API (authoritative results), with one test suite.
3. **AI pair-programming quality** — the build runs through Antigravity with Gemini models, whose code generation is strongest in the TypeScript/React ecosystem.
4. **Passkeys are first-class here** — SimpleWebAuthn on the server and established React Native passkey support on the client.
5. **Market fit** — TypeScript + React Native + Node + PostgreSQL is the most common stack in the roles this portfolio project targets.

## Alternatives considered

- **Flutter + Dart** — polished UI and one client language, but Dart serves only the client: the API and engines would need a second language and the engines could not be shared with the app. Passkey ecosystem is thinner. Rejected.
- **Fully native (Swift + Kotlin)** — best native SDK story, but two codebases doubles the cost of every feature for a solo builder. Rejected.
- **Python/FastAPI API** — a good stack that loses the shared-engines property, the main architectural selling point. Rejected.

## Consequences for later steps

- **Step 4 (hello-world end-to-end)** must scaffold the monorepo, run `expo prebuild`, and prove a *development build* running on a device — not Expo Go.
- **Step 7 (Entrust ATO recovery)** starts with a de-risking spike: wrap a minimal Entrust SDK call in the local module and run it in the dev build before designing the full recovery flow.
- **Step 6 (passkeys)** needs a real domain for the WebAuthn RP ID, with the Apple App Site Association file and Android Digital Asset Links hosted on the API domain. Local development can use a tunnel; the domain decision lands with Step 6.
